Relatório Teórico: Estratégias de Teste em APIs REST com Java e Spring Boot1. Introdução aos Testes de Software1.1. Diferenciação Conceitual: Defeito, Erro e FalhaNo ciclo de desenvolvimento de software, é fundamental distinguir os conceitos de erro, defeito e falha:   Erro: Uma ação ou engano humano cometido durante a fase de análise, design ou codificação. Por exemplo, um desenvolvedor esquecer de tratar um valor null ou inverter uma condição lógica if (preco < 0).   Defeito (ou Bug): É a imperfeição ou anomalia concreta no código-fonte, resultante do erro humano. A linha de código incorreta no repositório representa o defeito.   Falha: É o comportamento incorreto ou inesperado manifestado pelo sistema durante a sua execução, decorrente de um defeito. Ocorre quando o usuário ou uma aplicação cliente faz uma requisição HTTP à API e recebe um erro status 500 Internal Server Error ou um cálculo de valor incorreto.   1.2. A Pirâmide de TestesA Pirâmide de Testes é um modelo conceitual que orienta a distribuição e proporção ideal das diferentes categorias de testes automatizados:   Base (Testes Unitários): Representa a maior quantidade de testes do sistema. São rápidos, baratos de criar e executar, e rodam de forma isolada sem dependências externas.   Meio (Testes de Integração e Serviço): Focam na verificação da comunicação correta entre múltiplos componentes do sistema (ex.: comunicação entre a classe de serviço e a base de dados).Topo (Testes de Sistema / E2E): Testam o fluxo completo de ponta a ponta, simulando o uso real. São mais complexos, lentos de executar e mais caros de manter.1.3. O Ciclo de Feedback Rápido e CI/CDA automação de testes integrada a uma esteira de Integração Contínua e Entrega Contínua (CI/CD) garante que cada alteração efetuada no código seja validada de forma imediata. O ciclo de feedback rápido permite que defeitos sejam identificados em poucos minutos após o commit, reduzindo drasticamente o custo de correção e impedindo que código instável chegue ao ambiente de produção.   2. Testes Unitários (Unit Testing)2.1. Conceito e Isolamento de DependênciasTestes unitários visam validar a menor unidade testável de código (geralmente um método individual de uma classe) de forma totalmente isolada. Para garantir a velocidade e o isolamento, todas as dependências externas — como bancos de dados, chamadas a APIs de terceiros ou serviços do ecossistema — devem ser substituídas por objetos simulados (mocks).   2.2. Aplicação Prática no Spring BootNo desenvolvimento com Spring Boot, a camada de regras de negócio (@Service) é o principal alvo dos testes unitários. Para testar uma classe @Service sem carregar o contexto completo do Spring Framework (o que tornaria o teste lento), utilizamos as seguintes ferramentas:   JUnit 5: Framework de testes responsável por estruturar os métodos de teste, asserções (assertEquals, assertThrows, assertNotNull) e ciclo de vida (@Test, @BeforeEach).   Mockito: Framework de mocking utilizado para simular o comportamento das dependências da classe testada.   Anotações Chave:@ExtendWith(MockitoExtension.class): Habilita a integração do Mockito ao ciclo de vida do JUnit 5.   @Mock: Cria uma instância simulada de uma dependência (ex.: a interface do repositório @Repository).   @InjectMocks: Cria a instância da classe a ser testada e injeta automaticamente os objetos anotados com @Mock.   3. Testes de Sistema e Integração (System/Integration Testing)3.1. Definição, Escopo e ComparativoOs testes de integração e sistema avaliam a integração correta entre diferentes partes da aplicação (serviços, repositórios, controladores, banco de dados e contratos REST).   Comparativo: Enquanto os testes unitários garantem a lógica isolada de um método em milissegundos, os testes de integração garantem que os componentes funcionam em conjunto com maior confiabilidade de infraestrutura, porém com menor velocidade de execução.   3.2. Aplicação Prática no Spring BootNo Spring Boot, a validação do fluxo completo desde o recebimento da requisição HTTP até a gravação na base de dados utiliza as seguintes estratégias:   @SpringBootTest: Carrega o contexto de aplicação Spring completo para execução dos testes.   @AutoConfigureMockMvc: Configura automaticamente o ambiente simulado para realização de requisições HTTP.   Banco de Dados em Memória (H2) ou Testcontainers: Em vez de usar a base de dados de produção, os testes de integração utilizam uma base em memória rápida (como H2) para gravar e consultar dados temporários durante os testes, garantindo um ambiente limpo a cada execução.   4. Teste de Caixa Preta (Black-box Testing)4.1. Abordagem Baseada em EspecificaçãoO Teste de Caixa Preta analisa a aplicação focando estritamente nas entradas, saídas e contratos de interface, sem levar em consideração o conhecimento do código-fonte ou da estrutura interna dos métodos.   4.2. Aplicação Prática no Spring BootNo contexto de APIs REST, os testes de caixa preta focam nos endpoints definidos na camada @RestController:   Validação de DTOs e JSON: Verificação do correto mapeamento e validação dos dados de envio e resposta (Data Transfer Objects).   Status HTTP e Headers: Garantia de que respostas com sucesso retornam códigos como 200 OK ou 201 Created, e requisições inválidas retornam 400 Bad Request ou 404 Not Found.   Ferramentas (MockMvc ou RestAssured): Utilizadas para simular as chamadas HTTP (POST, GET, PUT, DELETE) e inspecionar os retornos da API via validação de campos JSON (jsonPath).   5. Teste de Caixa Branca (White-box Testing)5.1. Abordagem Baseada em Estrutura InternaO Teste de Caixa Branca foca na análise da estrutura interna do código. O objetivo é garantir a cobertura de todos os caminhos possíveis de execução, verificando estruturas condicionais (if/else), laços de repetição (for/while) e tratamento de exceções.   5.2. Medição de Cobertura de Código no Spring BootA verificação de caixa branca no ecossistema Java/Spring é realizada com ferramentas de medição de cobertura de código (Code Coverage), como o JaCoCo (Java Code Coverage).   Funcionamento: O JaCoCo analisa as classes compiladas e monitora quais linhas e ramificações condicionais foram executadas pela suíte de testes automatizados.   Relatórios: Gera relatórios detalhados (ex.: em HTML) indicando a porcentagem de código coberta por testes e sinalizando eventuais trechos de código ou exceções que ainda não foram devidamente exercitados na suíte de testes.
